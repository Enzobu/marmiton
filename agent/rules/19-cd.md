# CD Dokploy — règles de déploiement

> À appliquer uniquement aux projets ayant explicitement choisi **production seule** ou **préproduction + production**. Aucune action réelle sur Dokploy n'est autorisée par le seul fait d'installer les règles.

## CD01 — Choix préalable

Demander explicitement pour chaque projet : production seule, ou préproduction + production. Ne pas configurer la préproduction sans accord.

## CD02 — Dokploy

Utiliser Dokploy comme cible de CD par défaut; distinguer les applications Compose des autres types.

## CD03 — Prod seule

En mode production seule, créer uniquement le job et l'environnement production; ne pas créer de branche pre-prod.

## CD04 — Deux environnements

En mode dual, créer les jobs preprod et prod, chacun avec ses identifiants Dokploy séparés.

## CD05 — Branche préprod

Déclencher la préproduction par push sur refs/heads/pre-prod, jamais depuis une pull request.

## CD06 — Tags prod

Déclencher la prod seulement par push sur des tags de release vX.Y.Z validés, pas sur un merge direct.

## CD07 — Branche source du tag

Exiger que le tag appartienne à la stratégie de release autorisée et corresponde à un commit validé.

## CD08 — CI obligatoire

Les jobs CD dépendent d'un véritable ci-required du même run et même SHA, sans faux job de validation.

## CD09 — CI sur références

Exécuter la batterie complète de CI sur tags de production et sur pre-prod lorsque celle-ci existe.

## CD10 — Environnements GitHub

Utiliser GitHub Environment production ou pre-production avec restrictions et approbations prises en charge par le plan.

## CD11 — Secrets isolés

Stocker DOKPLOY_API_KEY et DOKPLOY_COMPOSE_ID dans les secrets de chaque GitHub Environment.

## CD12 — URL paramétrable

Paramétrer DOKPLOY_URL et APP_HEALTH_URL par environnement; imposer HTTPS et ne pas coder de domaine personnel en dur.

## CD13 — Compose deploy

Pour Compose, appeler POST /api/compose.deploy avec x-api-key et JSON contenant composeId; ne pas utiliser freshVolumes.

## CD14 — Autres applications

Pour un type Dokploy différent de Compose, rechercher et valider l'endpoint officiel approprié.

## CD15 — Préflight

Contrôler valeurs, Compose ID, instance, référence et droits avant de déclencher une opération.

## CD16 — Version exacte

Vérifier que la source Dokploy suit exactement la branche/tag/commit ou digest immuable testé. Bloquer lorsque Dokploy suit main tandis que GitHub valide un tag.

## CD17 — Statut HTTP

Ne considérer qu'une réponse 2xx comme acceptation du déclenchement, pas comme déploiement terminé.

## CD18 — Logs sobres

Ne jamais afficher la clé API ou la réponse brute Dokploy potentiellement sensible dans les logs.

## CD19 — Pas de retry aveugle

Ne pas rejouer automatiquement un POST de déploiement lorsque le résultat est incertain.

## CD20 — Concurrency

Sérialiser par projet et environnement avec cancel-in-progress false; ne pas annuler un déploiement actif.

## CD21 — Token GitHub

Limiter les permissions du GITHUB_TOKEN à contents: read sauf besoin justifié.

## CD22 — Actions épinglées

Épingler les actions externes à des SHA complets vérifiés.

## CD23 — Statut réel

Corréler un identifiant de nouveau déploiement Dokploy à son état terminal avant d'annoncer la réussite.

## CD24 — Healthcheck

Effectuer un contrôle de santé après déploiement terminé, avec délais bornés; ne pas confondre santé et bonne version.

## CD25 — Niveaux de preuve

Distinguer déclenché, terminé, sain, version vérifiée dans les rapports.

## CD26 — Backups

Prévoir sauvegarde et restauration vérifiables avant modification destructive de DB ou volumes.

## CD27 — Migrations

Planifier les migrations compatibles et ne jamais lancer de migration destructive implicite.

## CD28 — Rollback

Documenter la marche arrière vers une version précédente et les risques sur les données.

## CD29 — Traçabilité

Tracer environnement, SHA, tag, identifiant Dokploy, résultat et lien d'exécution sans fuite de secret.

## CD30 — Approbation prod

Par défaut les tags autorisés peuvent déployer après CI; ajouter une approbation manuelle selon choix utilisateur et disponibilité GitHub.

## CD31 — Configuration par projet

Adapter URL, source, IDs, stratégie de release, healthchecks et prérequis; ne pas partager les secrets entre projets.

## CD32 — Bibliothèque inactive

Le dépôt agent-rules ne doit jamais déclencher un déploiement sur push, PR ou tag; seules des règles et modèles inactifs y résident.

## CD33 — Jobs nommés

Utiliser deploy-prod et, en mode dual, deploy-pre-prod; la logique peut être partagée dans un script testé.

## CD34 — Timeouts

Utiliser délais réseau et timeout de job bornés sur runners GitHub-hosted.

## CD35 — Vérification

Valider syntaxe des workflows, gates et conditions puis observer un run réel avant d'affirmer que la CD fonctionne.

## CD36 — Pas d'action implicite

Installer un workflow n'autorise pas à créer un tag, pousser sur pre-prod ou appeler Dokploy sans demande correspondante.

Références : [Dokploy Compose API](https://docs.dokploy.com/docs/api/reference-compose), [Dokploy Deployment API](https://docs.dokploy.com/docs/api/reference-deployment).

## CD37 — Données Dokploy et chemins de sauvegarde

Pour les données persistantes des projets Dokploy, utiliser des bind mounts vers `/etc/dokploy_volume/<APP>/<donnée>` par défaut et déclarer tous les chemins dans `.env.example` selon [ENV01–ENV20](20-environment.md). Préserver les chemins et la stratégie de sauvegarde existants sans migration ou interruption de service non demandée.
