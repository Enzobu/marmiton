# CI — Continuous Integration (sans CD)

> **CI seulement.** Les pipelines valident le code : aucun déploiement, publication d'image, release, écriture en production, migration de production ou promotion d'environnement. Les règles ci-dessous définissent les exigences; leur traduction en GitHub Actions dépend de chaque dépôt. Les contrôles sont obligatoires lorsqu'applicables, avec exceptions documentées et approuvées plutôt que désactivation silencieuse.

## CI01 — Déclencheurs
Déclencher la CI sur `pull_request` ciblant `dev` et `main` et sur `push` vers ces deux branches **lorsqu'elles existent**. Sur un dépôt sans `dev`, n'exiger que la branche par défaut. Éviter les exécutions inutiles sur chaque branche temporaire, sauf besoin documenté.

## CI02 — Aucun CD
La CI n'emploie ni SSH de production, ni jeton de déploiement, ni action de release, ni push de container vers une registry, ni publication vers un store, ni déploiement de base. Les builds de validation restent locaux au runner; conserver des artefacts de diagnostic temporaires ne constitue pas une publication de release.

## CI03 — Batterie complète
Sur chaque PR, exécuter **toutes les suites configurées et applicables**, sans filtrer uniquement les fichiers modifiés : lint, format-check, typecheck, analyse statique, unitaires, intégration, E2E, tests de migrations, Postman, Bruno, build et Docker selon le projet.

## CI04 — Jobs isolés et parallèles
Séparer au minimum qualité, tests, sécurité, build, contrôle API et conformité si les outils existent. Exécuter les jobs indépendants en parallèle; déclarer les dépendances nécessaires entre démarrage API/DB et tests d'API.

## CI05 — Contrôle final unique
Prévoir un job final stable (ex. `ci-required`) qui agrège les résultats des jobs attendus et échoue pour tout job obligatoire en échec, annulé ou **skipped de façon inattendue**. Un contrôle non applicable doit être explicitement justifié et traité comme tel, jamais passé silencieusement.

## CI06 — Branch protection / Rulesets
Configurer des GitHub Rulesets ou branch protection sur `dev` et `main` (selon existence) : PR obligatoires, contrôle final requis, blocage sur échec, protection contre push direct et force push. L'agent ne peut pas garantir les protections avec un simple fichier; demander/contrôler la configuration GitHub réelle.

## CI07 — Qualité
Exécuter les linters, vérificateurs de format, analyseurs de types et analyse statique déjà définis par le projet. L'absence d'un outil n'est pas un succès : déclarer `non applicable` si stack incompatible, ou proposer son ajout si contrôle attendu mais non configuré.

## CI08 — Tests
Exécuter unitaires, intégration, E2E, tests de régression et migration quand ils existent ou sont exigés par les fonctionnalités. Ne pas sauter silencieusement une suite lente; timeouts raisonnables et diagnostics en cas de délai dépassé.

## CI09 — Couverture
Produire un rapport de couverture quand un outil existe. Publier un résumé vérifiable et des artefacts temporaires; ne pas inventer un seuil de couverture universel. Choisir un seuil de projet ou une politique d'absence de régression de couverture explicite.

## CI10 — Postman et Bruno
Pour toute API HTTP, **deux jobs distincts** exécutent toutes les collections `testing/postman` et `testing/bruno` contre l'API démarrée en local sur runner. Respecter `rules/17-api-testing.md`. Absence d'une collection, scénario ou assertion requis = échec de conformité; ne pas remplacer par la seule validation OpenAPI.

## CI11 — Environnement API unique
Utiliser le seul environnement versionné `<nomProjet>_local` pour **chaque outil**. En CI, remplacer au runtime `baseUrl` et variables sensibles par les options du runner, sans générer/committer un nouvel environnement `ci`, `test` ou `staging`. Les versions Postman/Bruno doivent supporter les options utilisées; vérifier leurs CLI.

## CI12 — Services de test isolés
Lancer DB, cache, broker et API nécessaires en services ou conteneurs temporaires, avec données factices, schéma et fixtures reproductibles. Attendre la readiness réelle avant tests. Interdire l'accès à une DB ou API de production depuis les tests CI.

## CI13 — Tests d'erreurs API
Vérifier nominal + validation, auth 401/403, not-found, conflits, erreurs métier, et tests d'état selon pertinence. Les deux collections doivent partager une matrice de scénarios traçable; les échecs de scénarios font échouer le job concerné.

## CI14 — Secrets
Scanner les changements et si pertinent l'historique avec un détecteur tel que Gitleaks. Aucun secret réel dans artefacts, logs, environnements de collections ou résumés; masquer les valeurs et interdire leur impression.

## CI15 — Audit dépendances
Utiliser un audit adapté au langage (npm audit, Composer audit, OSV-Scanner ou équivalent). Politique initiale : bloquer **nouvelles** vulnérabilités high/critical confirmées, avec baseline et exceptions tracées, datées et expirables. Ne pas ignorer le passif silencieusement.

## CI16 — SAST
Activer CodeQL ou Semgrep quand la stack et les fonctionnalités du dépôt le permettent. Exécuter avec permissions minimales et contrôles de qualité adaptés, sans supposer la disponibilité de fonctionnalités payantes.

## CI17 — Dependency Review
Examiner les changements de dépendances dans les PR avec les capacités GitHub disponibles; si l'outil n'est pas accessible dans un dépôt privé/plan donné, documenter une alternative au lieu de déclarer le job réussi.

## CI18 — Sécurité des workflows
Valider les workflows avec `actionlint` et utiliser `zizmor` ou équivalent lorsqu'il est disponible; interdire scripts interpolant directement les champs non fiables de PR dans le shell.

## CI19 — Permissions GitHub minimales
Définir `permissions: contents: read` (ou équivalent nécessaire) par défaut; n'élever les droits que pour un job justifié. Ne pas employer `pull_request_target` pour exécuter du code non fiable avec des secrets, et ne jamais exposer de secrets aux PR de forks non fiables.

## CI20 — Dépendances de workflows figées
Épingler les actions tierces à des SHA complets validés, annoter la version lisible et contrôler les mises à jour. Éviter les dépendances à des tags flottants dans les workflows de projets sécurisés.

## CI21 — Runners
Utiliser par défaut les runners GitHub-hosted. Ne pas exécuter de code PR non fiable sur les serveurs personnels, home-lab ou runners persistants privés sans isolation sérieuse et autorisation.

## CI22 — Cache sûr
Mettre en cache uniquement les caches de gestionnaires (npm/pnpm/Composer/pub/Gradle/etc.) avec clés liées aux lockfiles et contrôles d'accès adaptés; ne jamais y mettre de secrets ni réutiliser aveuglément un cache non fiable entre contextes privilégiés.

## CI23 — Concurrency
Configurer `concurrency` par PR/ref pour annuler les runs PR obsolètes; ne pas annuler des runs de branches protégées ou distinctes par une clé trop générique.

## CI24 — Rapports
Fournir logs lisibles, résumés et rapports JUnit/coverage lorsque les outils les produisent; conserver des artefacts de diagnostic de courte durée, sans secrets. Les résultats Postman et Bruno sont distincts, et les tests échoués doivent être identifiables.

## CI25 — PR feedback
Rendre l'état des vérifications directement visible dans GitHub Checks. Un commentaire automatique n'est utile que s'il est maintenu à jour et qu'il n'ajoute pas du bruit; ne pas accorder de write token par défaut uniquement pour commenter.

## CI26 — Matrices de versions
Tester la version de runtime réellement supportée, et plusieurs versions si le projet déclare une plage de compatibilité. Éviter une matrice coûteuse non pertinente.

## CI27 — Builds
Compiler et assembler l'application pour la cible prévue, sans publication ni déploiement. L'échec de compilation bloque la validation de la PR.

## CI28 — Docker et Compose
Si Docker/Compose est présent, vérifier Dockerfiles avec Hadolint ou équivalent, `docker compose config` en évitant toute sortie secrète, construire les images et analyser les vulnérabilités avec Trivy ou équivalent. Contrôler absence de `version` et `restart: unless-stopped` par défaut, en tenant compte des services one-shot explicitement justifiés.

## CI29 — Analyse des images
Bloquer les vulnérabilités critiques/élevées **nouvelles et exploitables selon la politique projet**, avec exceptions temporaires auditées; ne pas considérer une analyse impossible comme réussie. Ne jamais pousser l'image analysée.

## CI30 — Conformité
Vérifier présence et validité des fichiers requis selon stack (collections, environnements, contrats OpenAPI, JSON/YAML, docs, conventions), sans tests fantômes ni dépendance excessive à une simple détection par extension.

## CI31 — Stack PHP / Symfony
Lancer les contrôles configurés : PHPUnit, PHPStan/Psalm, PHP-CS-Fixer/PHPCS, Symfony lint, Composer audit, migrations sur base éphémère, builds d'assets si présents, Postman et Bruno si API exposée.

## CI32 — Stack NestJS
Exécuter Jest (unit + intégration/E2E), ESLint, Prettier check, TypeScript, build, npm/pnpm audit, tests Prisma/MariaDB si nécessaires, Postman et Bruno contre une API lancée en local.

## CI33 — Stack React / Vite
Exécuter Vitest/Jest, ESLint, Prettier check, TypeScript, build Vite et E2E configurés; ne pas imposer Postman/Bruno à un frontend pur sans API HTTP développée dans le dépôt.

## CI34 — Stack Flutter
Exécuter `flutter analyze`, `dart format --output=none --set-exit-if-changed .`, `flutter test`, tests d'intégration disponibles et build Android approprié aux runners (iOS uniquement sur runner macOS si applicable). Ne jamais publier sur stores.

## CI35 — MariaDB / Prisma
Démarrer une base temporaire, appliquer migrations réelles, contrôler schéma/fixtures et tests dépendants. Ne pas toucher aux bases partagées ni à la production.

## CI36 — Sonar optionnel
Activer SonarQube/SonarCloud si le dépôt dispose d'une instance, des permissions et de secrets sûrs; la CI doit refléter le Quality Gate lorsqu'il est configuré. Aucune obligation de provisionner Sonar.

## CI37 — Performance ciblée
Ajouter tests de performance/régression sur modules critiques avec budgets et seuils mesurables; éviter les benchmarks non déterministes comme blocage universel de PR.

## CI38 — Gestion des outils manquants
Un contrôle obligatoire **applicable** ne peut pas être converti en `continue-on-error: true` ou `if: false` pour passer au vert. Une vraie non-applicabilité doit être explicitement décrite dans la configuration; une absence de runtime, service ou runner est une erreur d'installation à corriger.

## CI39 — Vérification du workflow
Avant de déclarer la CI opérationnelle, valider la syntaxe YAML et la structure des jobs, puis observer au moins un vrai run sur PR. Sans runner/exécution, le résultat reste « non vérifié »; un workflow committé n'est pas une preuve de succès.

## CI40 — Gouvernance et exceptions
Documenter les contrôles requis, seuils, versions supportées et exceptions dans le dépôt applicatif. Les dérogations de sécurité doivent être motivées, limitées dans le temps et examinées; ne jamais modifier un seuil uniquement pour faire passer une PR.
